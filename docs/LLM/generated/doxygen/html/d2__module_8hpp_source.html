32 // Modules are there to solve two problems:
33 // 1. isolating state for specific features
34 // 2. isolating platform behavior
35 // A module is supposed to be responsible for a specific task and provide an easy way to
36 // describe requirements, dependencies or behavior. This includes:
37 // 1. lifecycle - i.e. Status
38 // 2. compatibility (from best to worse) -
39 // a) Native
40 // b) Generic
41 // c) Unknown
42 // d) Failed
43 // 3. Access - whether it is thread safe or not (so only main thread). You can also add any
44 // "safe threads" manually at runtime
45 // 4. Load - Lazy (on query) or Immediate (at IOContext startup/module load)
46 // 5. Dependencies (on other modules)
47 // ------------------------------------------------------
48 // ModuleDecl is used to just declare (an abstract) module (so interface)
49 // ModuleImpl is for the actual implementation of the module
50 // For platform independent module 'Module' simply combines both
